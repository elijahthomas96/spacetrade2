## Decisions made during the build

- **Folder layout.** `SpaceTrade.Sim` in `game/Assets/Scripts/Sim/`, `SpaceTrade.Game` in `game/Assets/Scripts/Game/`, `SpaceTrade.Sim.Tests` (EditMode) in `game/Assets/Tests/EditMode/`, `SpaceTrade.Game.Tests` (PlayMode) in `game/Assets/Tests/PlayMode/`.
- **Marker classes.** Unity does not build an assembly with no code, so `SimAssemblyMarker` and `GameAssemblyMarker` (empty classes, no logic) exist so both assemblies compile and tests can find them.
- **Guard tests.** `ScaffoldTests.SimAssembly_DoesNotReferenceUnityEngine` fails if `SpaceTrade.Sim` ever references a `UnityEngine` or `UnityEditor` assembly. `IntegerStateGuardTests.SimAssembly_StoresNoFloatingPoint` fails if any class in `SpaceTrade.Sim` has a `float`, `double`, or `decimal` field.
- **Empty folders.** `Art`, `Audio`, and `StreamingAssets` each hold a `.gitkeep` so git keeps them. Unity ignores files starting with a dot.
- **Packages.** Test Framework 1.8.0 and Input System 1.20.1 were already installed by the Universal 2D template; nothing was added.
- **Tutorial leftovers removed (session 2, owner's decision).** Deleted `Assets/Welcome/`, `Assets/Scenes/` (with `SampleScene`), the package `com.unity.learn.iet-framework`, and its settings folder. The build scene list is empty until session 11 adds the startup scene. The URP render settings and scene template in `Assets/Settings/` are kept.
- **Time code layout (session 2).** Namespace `SpaceTrade.Sim.Timing` (named "Timing", not "Time", so it never clashes with Unity's `Time` class): `GameTime` (unit constants, real-time-at-speed helper), `GameDate` (calendar), `ClockSpeed` (only `X1`, `X3`, `X5`), `SimClock` (tick, speed, paused), `TransitMath`, `IRealTimeSource`, `RealTimeDriver`. Namespace `SpaceTrade.Sim.Events`: `EventPhase`, `SimEvent`, `EventQueue`. `Simulation` and `CommandResult` sit in `SpaceTrade.Sim`.
- **Clock commands.** `Pause`, `Play`, and `SetSpeed` are commands on `Simulation` returning a `CommandResult` (success, or failure with a reason). Setting any speed other than 1x, 3x, or 5x is refused and changes nothing. Setting a speed while paused selects it but stays paused; Play resumes at the selected speed. Pausing when already paused (or playing when already playing) succeeds and changes nothing. A new `Simulation` defaults to tick 0, 1x, not paused; session 7 decides the new-game start state.
- **Event ordering.** Same tick: phase (arrival, market replenishment, in-system transport, automated departure), then entity id (ship id, or system id for market events), then the order the events were scheduled. Events scheduled while `Advance` is running are processed in the same call if they fall in range. `Advance` refuses to go backward, an event may not call `Advance`, and nothing may be scheduled in the past.
- **Real-time driver.** Reads a monotonic clock in whole microseconds. Elapsed real microseconds x speed go into a carry; every whole 1,000 becomes one tick passed to `Advance`, the remainder is kept. Real time that passes while paused is discarded. If the time source ever reads earlier than before, nothing advances. The driver's `Pause`, `Play`, and `SetSpeed` first count the time already elapsed at the old setting, then apply the command; the game should send clock commands through the driver. The driver's carry (less than one tick) is not part of saved state.
- **Rounding.** Transit ticks and real-time-remaining both round up, so a countdown never shows zero before the arrival.
- **Reachability and `maxHopMilliLy` (session 3, owner's decision).** New tuning field `galaxy.maxHopMilliLy`, default 7000 (7 ly). A system is reachable if a chain of hops of at most `maxHopMilliLy` connects it to the start system, and the start system must be within `maxHopMilliLy` of a shipyard. Validation requires `maxHopMilliLy` to be at least `nearestNeighbourMaxMilliLy`, so generation can always succeed. No fuel logic yet (see notes for sessions 5 and 7). `docs/spec.md` sections 4 and 12 updated to match.
- **Tuning code layout (session 3).** Namespace `SpaceTrade.Sim.Tuning`: `TuningData` (one class per section, fields carry their unit in the name), `TuningDefaults` (built-in values), `TuningReader` and `ObjectReader` (per-field type and range checks), `TuningValidator` (checks across fields), `TuningWriter`, `TuningLoader` (`LoadText`, `LoadFile`, returns tuning, error list, and whether defaults were used). Namespace `SpaceTrade.Sim.Json`: a small strict JSON parser and writer written in the project (Newtonsoft is only present as another package's dependency, so it is not used). Numbers are kept as text and only whole numbers convert, so no floating point enters the simulation.
- **Tuning file rules (session 3).** Every value is a whole number with its unit in the field name. Food and water per person per day are in grams (whole kilograms are too coarse for voyages lasting years); ship sizes and freight caps are in whole tonnes. Missing, misspelled, and unknown fields are errors. Any error sets the whole file aside and the built-in defaults are used, with every error returned. Checks that compare fields with each other run only after every field reads cleanly. List items are named by id in errors, for example `commodities[ore].baseRatePerTonne`, and errors include the line number when known.
- **Tuning sections (session 3).** The sections in spec 12, plus a separate `industries` section (spec 4.1 says industry names and what they consume and produce are tuning data). Fields for later sessions' rules are defined now with their meaning in the guide: the distance factor is `distanceFactorBasePercent + distanceFactorPerLyPercent × light-years`; passenger pool room is `poolCapBasePassengers` plus `poolCapExtraPerTenMillionPopulation` per 10 million combined population, plus `hubPoolBonusPercent` from a population hub; `automation.recheckMinIntervalDays` limits how often a waiting ship is rechecked. Later sessions may add or adjust fields; when they do they must update `TuningDefaults`, the reader, the writer, `docs/tuning-guide.md`, the live `tuning.json`, and the test fixture together.
- **Default tuning values are a first draft (session 3).** Chosen to be plausible (for example, courier 60 t dry, 30 t hold, 20 t tank, 4 berths, 2 crew; starting credits 200,000; courier price 1,000,000). Session 18 balances them against the five targets.
- **Test fixture (session 3).** `game/Assets/Tests/EditMode/Fixtures/test-tuning.json`, generated from the defaults at the same time as the live file. Tests read it through `TestTuning`; no test reads the live `tuning.json` yet (session 7 adds the one allowed live-file test). Fixture changes happen only when a session adds or changes tuning fields.
- **Random numbers (session 3).** `SeededRandom` (xoshiro256** seeded through SplitMix64) is written in the project so a seed gives the same numbers on every machine. Its state is four whole numbers, ready to save. `System.Random` must not be used in the simulation.
- **Galaxy (session 3).** Namespace `SpaceTrade.Sim.World` (not "Galaxy", to avoid a clash with the `Galaxy` class): `Galaxy`, `StarSystem`, `GalaxyGenerator`, `GalaxyRules`. Positions are whole milli-ly, shifted so the smallest x and y are 0; distances are the integer square root rounded to the nearest milli-ly (`IntMath`). Placement: each new system goes between the nearest-neighbour minimum and maximum from a random existing system, and at least the minimum from all others. Shipyard systems are chosen first and always get at least one trading industry next to their shipyard works. The start system is picked at random from systems within `maxHopMilliLy` of a shipyard. A candidate that fails any guarantee in `GalaxyRules` is thrown away and the next is drawn from the same random stream; after 10,000 failed candidates generation stops with a message pointing at the tuning. Industries are stored by id; a system has a shipyard exactly when it has an industry with `enablesShipyard`.

- **Market starting fill (session 4, owner's decision).** New tuning fields `start.marketStartFill.supplyPercent`, `demandPercent`, `passengerPercent`, each 0 to 100 (checked by the reader, field-named error), default 100. A new market's stocks start at that percent of their caps.
- **Provision prices (session 4, owner's decision).** Each system's fuel, food, and water roll (a whole percent in the `priceRoll` range) is made once when the market is created and never re-rolled. Only the roll is stored; the price is worked out each time from the current tuning base price, the industry modifiers, and the roll, so tuning edits reach existing saves.
- **Combined industry modifier (session 4, owner's decision).** The modifiers of every industry in a system multiply, then the result is clamped to new tuning fields `provisions.combinedModifierMinPercent` (default 50) and `combinedModifierMaxPercent` (default 200); the validator checks min is not above max. A system cannot list the same industry twice, so the "two refineries" test gives the agricultural system the refinery's 70 percent fuel modifier: 49 percent with a low floor, 50 percent with the default floor.
- **One rounding rule (session 4, owner's decision).** `IntMath.DivideRounded`: every market figure (rates, fares, provision prices, pool sizes, starting amounts) is built as one exact fraction of whole numbers and rounded once at the end to the nearest whole number, halves up. (Session 5 restated this as halves away from zero for every figure; same results for positive numbers.) Large products use `System.Numerics.BigInteger` (a whole-number type) so extreme tuning values cannot overflow.
- **Freight rates and fares store their roll too (session 4).** For the same reason as provisions (spec 12), offers and pools store only the rolled percent; the published rate is worked out from it and the current tuning. Re-rolls replace the percent. Rates and fares are whole percents in their roll range.
- **Market layout (session 4).** Namespace `SpaceTrade.Sim.Markets`: `Market` (state, queries, schedules, reservations), `MarketMath` (formulas), `MarketEvent`, entry classes (`CommodityStock`, `FreightOffer`, `PassengerPool`, `ProvisionRoll`), reservation classes. `Simulation.Market` is set by `Simulation.AttachMarket`, which schedules one market event per system. Freight is in whole tonnes. One offer per producer-consumer system pair (any distance); one passenger pool per ordered pair of systems. Supply is shared by every offer from that origin for that commodity; demand by every origin delivering there.
- **Market schedules (session 4).** Intervals count from `Market.CreatedTick`. Each system's single event runs, in order: supply and demand growth for each commodity whose own interval is due (tuning order), then passenger growth, then the re-roll of that system's outgoing offers and pools. Then it schedules itself for the system's next due tick. Same-tick systems run in system-id order (spec 8.1). Growth stops at the cap and never removes stock above a cap that tuning later lowered. The market has its own `SeededRandom`, seeded from the galaxy seed, so market rolls do not depend on galaxy generation's random stream.
- **Reservations (session 4).** `Market.TryReserve(request, out reservation)` takes freight lines (from one origin to one destination; duplicate lines for a commodity are added together) and a passenger count, checks everything first, then applies it all or nothing. Failures list every problem with numbers, for example "Only 30 t of ore available from Rhea to Marrow (supply 30 t at Rhea, demand 150 t at Marrow); requested 50 t." The reservation records the rate and fare published at that moment. `Market.Release` puts back exactly what was taken, once; it is for undoing inside the same command. `Market.DescribeState()` gives a fixed text dump of every stored market value, for exact state comparisons.

- **Rates stored as percents, kept (session 5, owner's decision).** Open offers and pools keep storing only their rolled percent (session 4). A dispatched voyage must store its freight rate per tonne and passenger fare as fixed credit amounts taken at dispatch (see the session 6 requirement below). Checked: session 4's `Market.TryReserve` already returns a `MarketReservation` whose `ReservedFreight.RatePerTonne` and `FarePerPassenger` are whole credit amounts read at that moment, not percents, so nothing in the market code stands in the way.
- **One rounding rule (session 5, owner's decision).** `IntMath.DivideRounded` rounds to nearest with exact halves away from zero, and now accepts negative numbers (profit per year). For positive numbers this is the same as session 4's "halves up", so no market figure changed. Deliberate round-ups are separate and named: transit ticks, real time remaining, and supplies needed (`IntMath.DivideCeiling`). Written into spec 5.5 and the tuning guide.
- **Provisioning readings (session 5, owner's decisions).** (1) Supplies needed round up to the whole kilogram. (2) Food and water count in the hold and loaded mass at what will be aboard after topping up, leftovers included. (3) Buying costs kilograms x price per tonne / 1,000, rounded once. (4) Each supply has one average price; a voyage is charged total cost x kg used / kg aboard, rounded once, and using everything left charges everything left, so zero quantity always means zero cost. A stock also refuses a cost with zero kilograms. (5) Profit per game year can be negative and rounds by the same rule. All in spec 6.3, 6.7, and the tuning guide.
- **Test-only setup (session 5, owner's decision).** `Simulation.AddShip`, `Simulation.SetCredits`, `SupplyStock.Add` and `SupplyStock.Use`, and the `Ship` and `SupplyStock` constructors are `internal`. `game/Assets/Scripts/Sim/AssemblyInfo.cs` grants internal access to `SpaceTrade.Sim.Tests` only. The guarantee is compile-time: the C# compiler refuses any call to these from `SpaceTrade.Game` (or any other assembly). `SetupAccessGuardTests` pins what that rests on: the internal-access list is exactly `SpaceTrade.Sim.Tests`, each setup member is internal, `Simulation`, `Ship`, and `SupplyStock` have no public property setters, and `Simulation`'s public methods are exactly `Advance, AttachMarket, FindShip, Pause, Play, Provision, Quote, Schedule, SetSpeed`. Any new public method fails that last test until it is added on purpose. Limit: .NET reflection (code inspecting itself at run time) can reach any member; no compile-time rule can stop that, so presentation code must not use reflection on the simulation.
- **Ship and quote code layout (session 5).** Namespace `SpaceTrade.Sim.Ships`: `Ship` (id from 1, name, class id, drive id, docked system, fuel/food/water `SupplyStock`), `SupplyStock` (kg, total cost, `CostOfUsing`), `ProvisioningMath` (formulas, `Compute` gives a `VoyageNeeds`). Namespace `SpaceTrade.Sim.Voyages`: `VoyagePlan`, `VoyageQuote` (with `SupplyQuote`, `QuotedFreight`), `VoyageQuoter` (internal; reached only through `Simulation.Quote`). `Format` gives tonnes ("3.36 t") and credits ("43,733") for messages. Class and drive stats are read from the current tuning by id. `Market.CheckReservation` returns the same problems `TryReserve` would, without reserving, and the quote includes them.
- **Quote problem order and fixes (session 5).** Berths, hold, tank, market availability, credits. Hold and tank fixes are the smallest: fewest tonnes of freight to unload; if no amount of freight is enough, fewest passengers to drop, then fewest tonnes with that many; if nothing works, the message says the destination is too far or out of range. The Provision command buys exactly the shortfall and is refused (changing nothing) unless the quote is feasible.
- **Starter-range check (session 5, owner's decision in session 3).** In `TuningValidator`, using the same `ProvisioningMath.Compute` as the quote. Errors name `ships[<starter class>].tankTonnes` or `.holdTonnes`. Defaults: 9,789 kg fuel of 20,000; 3,360 kg food and water of 30,000.

- **Rounding round-ups confirmed (session 6, owner's decision 1 on the session 5 questions).** Transit ticks, real time remaining, and supplies needed round up, as spec 5.5 already says. No change.
- **When supplies are used (session 6, owner's decision 2 on the session 5 questions).** Supplies are used up and expensed once, at arrival, through `SupplyStock.Use`; that is the only place supplies are used up (buying through Provision and the dispatch top-up still adds kilograms and cost; owner confirmed this reading). The in-flight remaining-supplies figure is a read-only query in `SpaceTrade.Sim` (`Simulation.RemainingSupplyKg`), worked out from the locked voyage terms and the current tick in whole kilograms, never stored or saved, changing nothing. At the dispatch tick it equals what is aboard; at the arrival tick it equals exactly what settlement leaves aboard. In spec 6.7 and 9.1.
- **Dispatch top-up yes/no (session 6, owner's decision 1a).** `Simulation.Dispatch(plan, buyTopUp)`. Yes buys exactly the quoted shortfall inside the transaction, ending in exactly the same state as Provision then Dispatch. No, with any supply short, refuses with the shortfall and its cost ("Test Courier is short of 8.514 t of fuel, 2.592 t of food for this voyage (top-up 41,911 credits). Press Provision first, or dispatch with the top-up.") and changes nothing. A route stop's automatic provisioning setting is this yes/no. In spec 6.6 and 8.
- **Mid-trip remaining-supplies rounding (session 6, owner's decision 2a).** Used so far = locked use x elapsed ticks / transit ticks, rounded once by the one rounding rule (nearest, halves away from zero); remaining = aboard - used so far. In spec 6.7.
- **Receipts kept (session 6, owner's decision 3a).** `Simulation.Receipts` keeps every receipt in arrival order; the save holds them all. In spec 6.7 and 11.1.
- **Empty voyages allowed (session 6, owner's decision 4a).** A voyage with no freight and no passengers can be dispatched by hand. It reserves nothing, pays zero, uses its supplies once, and its receipt shows the loss the quote showed. In spec 6.6.
- **Ships in transit (session 6).** `Ship.Voyage` holds the voyage in progress (null when docked) and `Ship.DockedSystemId` is empty (null) while in transit. The quote refuses a ship in transit ("Test Courier is in transit to Beta, arriving Y4 M01 D01. It can take a new voyage once it docks."), so Provision and Dispatch refuse it too, changing nothing. In spec 6.6.
- **Dispatch steps (session 6).** `Dispatch` calls `Simulation.Quote` and refuses unless feasible; checks the top-up choice; reserves with `Market.TryReserve` (the last step that can fail); checks that the reservation's freight revenue and fare equal the quote's, releasing the reservation and refusing if not (a safety check; with the same tick and tuning it cannot differ, so no test reaches it); builds the voyage; then, with nothing left that can fail, buys the shortfall (the same private step `Provision` uses), marks the ship in transit, and schedules its arrival event. Commands may be called from inside events (session 9's automated departures will).
- **Locked voyage terms (session 6).** `Voyage`: ship, origin, destination, distance, drive id, departure and arrival ticks, freight lines (`LockedFreight`: commodity, tonnes, rate per tonne taken from the `MarketReservation`), passengers and fare per passenger (from the reservation), and the kilograms of fuel, food, and water it uses (from the quote). Nothing is read from tuning after dispatch.
- **Arrival settlement (session 6).** `ArrivalEvent` (phase 1, by ship id) calls `Simulation.SettleArrival`: uses up the locked kilograms with `SupplyStock.Use`, adds the locked payout to credits, docks the ship at the destination, clears the voyage, and appends a `VoyageReceipt` (freight lines, passengers and fare, freight and fare revenue, each supply's kilograms and cost, departure and arrival ticks, elapsed ticks, net profit). The event is processed once and not rescheduled, so a voyage pays exactly once.
- **Whole-state dump (session 6).** `Simulation.DescribeState()` writes every stored value in a fixed text layout: clock, credits, next ship id, ships with their voyages, receipts, every pending event with the queue's scheduling counter, and the market. "Byte-identical" tests compare its UTF-8 bytes; session 10 can repeat them on real save files. `Simulation`'s public methods are now exactly `Advance, AttachMarket, DescribeState, Dispatch, FindShip, Pause, Play, Provision, Quote, RemainingSupplyKg, Schedule, SetSpeed` (each new one added to `SetupAccessGuardTests` on purpose); the guard tests also cover the new `Voyage`, `LockedFreight`, `VoyageReceipt`, and `ConsumedSupply` (internal constructors, no public setters).

- **In-system pay timing (session 7, owner's decision 1 on the session 6 questions).** Pay falls due after each full 10,000 ticks since the toggle went on. A partial day pays nothing; switching off then on restarts the count. `Ship.InSystemSinceTick` holds the tick it went on (null when off); `InSystemIncomeEvent` (phase 3, by ship id) pays the class's `inSystemDailyIncome` from the current tuning and schedules the next day; switching off removes the pending event (`EventQueue.RemoveWhere`, internal). A day completing at the same tick the toggle goes off is paid, because `Advance` processes that tick's events first. In spec 10.
- **New-game clock (session 7, owner's decision 2).** A new game opens paused at 1x at tick 0, Y1 M01 D01. In spec 3.1 and 6.4.
- **Starter ship name (session 7, owner's decision 3).** New top-level tuning list `shipNames` (24 default names; top level rather than under `start` because session 8's purchases use it too). The name is picked by the seed with its own `SeededRandom` (seed XOR a fixed salt), so galaxy and market rolls for a seed are unchanged, and stored on the ship (`Ship.Name` cannot change). Missing list: `shipNames: is missing`; empty list: `shipNames: must list at least one name for new ships`; both fall back to defaults. `TuningData`, defaults, reader, writer, validator, `docs/tuning-guide.md`, the live `tuning.json`, and the test fixture updated together (the live file and fixture still equalled the defaults exactly, so both were regenerated; the only change is the new list). In spec 6.4 and 12.
- **Opening rates held until the first dispatch (session 7, owner's decision 1a).** `Market.HoldsOpeningRates` is set by `NewGame` and cleared by the first successful `Dispatch`. While set, the start system's re-roll is skipped entirely (no random draws); every other system re-rolls normally. After the first dispatch the start port re-rolls at its next scheduled re-roll. Markets made directly with `Market.Create` do not hold. In spec 6.4 and 11.1.
- **What a job is (session 7, decision 2a).** One freight offer or one passenger pool from the start port, loaded with the most tonnes (or passengers, up to berths) for which `Simulation.Quote` shows no problem, found by binary search; every limit only gets harder as the load grows. `OpeningOffers.FindJobs` and `OpeningOffers.Check` (public, read-only). In spec 6.4.
- **Different tradeoffs (session 7, decision 3a).** Two feasible jobs to different destinations where one has strictly fewer transit ticks and the other strictly more net profit on its quote. Required whenever `minFeasibleJobs` is 2 or more. In spec 6.4 and the tuning guide.
- **Adjusting and failing (session 7, decision 4a with the owner's condition).** If the guarantee fails, every start-port offer and pool roll is raised by 1 percent (capped at its tuning maximum) and the check repeats; if too few jobs are feasible at all, raising cannot help (feasibility does not depend on rates) so it stops at once. If it still fails, edited tuning is set aside for that new game: `NewGameResult.Errors` names the fields to look at (for example `start.openingOffers.minFeasibleJobs: ... Look at start.startingCredits, start.marketStartFill, ships[courier].holdTonnes, ...`), `UsedDefaults` is true, and the game is built from the built-in defaults. A new game never fails on the defaults: `NewGame.CreateTryingSeeds` tries the next seed until the guarantee holds, and the seed used is the galaxy's seed, in `NewGameResult.SeedUsed` and printed at the start of the market's line in `DescribeState` (`seed=... start=... created=... openingHeld=...`).
